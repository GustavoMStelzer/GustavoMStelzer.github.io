O problema
que deu origem
ao helper.

Integrar uma aplicação C# com Oracle envolve tarefas que se repetem: preparar o comando, definir parâmetros, executar a rotina e transformar os resultados em objetos da aplicação.

Criei o Oracle Helper para reunir essas rotinas em uma classe reutilizável. Os repositórios passam a informar o nome da procedure ou function e seus parâmetros, enquanto o helper concentra os detalhes da execução.

O projeto também faz o mapeamento de colunas de um RefCursor para propriedades C#, considerando diferenças de escrita dos nomes e conversões entre os tipos retornados pelo Oracle e os tipos do modelo.

01 / EXECUÇÃO

Procedures e functions

Chamadas assíncronas com parâmetros nomeados, além de rotinas com múltiplas saídas.

02 / MAPEAMENTO

RefCursor para objetos

Leitura dos resultados e preenchimento das propriedades do modelo usando reflection.

03 / CONVERSÃO

Tipos e valores nulos

Tratamento de DBNull, tipos Oracle e propriedades anuláveis na transformação dos resultados.

Como o helper
entra no repositório.

Exemplos simplificados com um pacote PL/SQL de demonstração. O site exibe os trechos; a execução acontece em uma aplicação .NET conectada ao Oracle.

                    var parametros = new Dictionary<string, object?>
{
    ["P_SITUACAO"] = "PENDENTE"
};

var servicos = await OracleHelper
    .ExecutarRefCursorAsync<ServicoDto>(
        conexao,
        "PCK_PORTFOLIO_DEMO.SP_LISTAR",
        parametros);

// O retorno é uma List<ServicoDto>.
                  
                
                  
                    // Function com retorno VARCHAR2.
                    var descricao = await OracleHelper
    .ExecutarFunctionAsync(
        conexao,
        "PCK_PORTFOLIO_DEMO.FC_DESCRICAO",
        new Dictionary<string, object?>
        {
            ["P_CODIGO"] = 101
        });

// O retorno é uma string.
Console.WriteLine(descricao);
                
                  
                    // Procedure simples, sem parâmetro OUT.
                    await OracleHelper.ExecutarProcedureAsync(
    conexao,
    "PCK_PORTFOLIO_DEMO.SP_VALIDAR",
    new Dictionary<string, object?>
    {
        ["P_CODIGO"] = 101
    });

// Conclusão normal: rotina executada.
                    // Erros Oracle são propagados à aplicação.

Estrutura do projeto

Uma rotina para cada tipo de chamada.

Método Responsabilidade
ExecutarRefCursorAsync<T> Retornar uma lista de objetos a partir de um RefCursor.
ExecutarRefCursorIDAsync<T> Obter o primeiro registro mapeado, quando existir.
ExecutarRefCursorComSaidasAsync<T> Tratar registros e parâmetros de saída na mesma chamada.
ExecutarFunctionAsync Executar uma function com retorno textual.
ExecutarProcedureComSaidasAsync Executar uma procedure e reunir seus parâmetros de saída.
ExecutarBlocoBooleanoAsync Executar um bloco PL/SQL com retorno numérico 0 ou 1 e convertê-lo para bool.

Uma decisão de implementação: o mapeamento normaliza os nomes das colunas e das propriedades. Assim, CD_SERVICO pode ser associado a CdServico.

O projeto para download contém a classe, um exemplo de console e um pacote PL/SQL com dados fictícios. As características e os limites da implementação estão documentados no README.

Decisões e limites

O que vale olhar no código.

Parâmetros pelo nome

As chamadas usam BindByName. O repositório informa a rotina e os valores; a classe concentra preparação, execução e leitura do retorno.

Falhar com contexto

Uma conversão inválida lança DataException com a coluna e a propriedade envolvidas. A exceção original é preservada, evitando devolver silenciosamente um objeto incompleto.

Mapeamento explícito

Nomes como CD_SERVICO e CdServico são normalizados. Colunas ambíguas geram erro; propriedades sem setter público e indexadores são ignorados.

Responsabilidades separadas

A aplicação controla a conexão e a transação. A classe organiza chamadas Oracle; regras do negócio continuam nas camadas responsáveis por elas.
